# 双 ESP32 语音、头显与车载屏方案

骑士 App 统一算路，通过蓝牙将同一条导航指引独立发给小智头显和车载屏。小智保留唤醒、语音对话和自提结果播报。这是下一步集成方案。现有 iPhone 已与单路蓝牙测试接收器核对「67 米后右转」，双板并行和实体 HUD 显示待验收。

## 设备与职责

| 设备 | 负责 | 当前基础 |
| --- | --- | --- |
| 骑士 iPhone App | 通过高德 SDK 定位和算路，在手机显示完整地图，分别向两块板发送下一步转向、距离和状态 | 已有高德骑行导航和一路头显 BLE 发送 |
| 小智 ESP32-S3 AI-MAIN | 通过 Wi-Fi 运行语音，通过 BLE 接收导航，在头盔 HUD 上显示箭头、距离和必要状态 | 已有语音、显示驱动和订单回执 BLE 特征，待增加导航特征及 HUD 绘制 |
| 车载 ESP32 | 通过 BLE 接收同一份指引，驱动车把或车载屏 | 兼容 SSD1306 128×64 I²C OLED 的接线可复用现有固件，其他屏需匹配驱动 |
| 可选 Mac 服务 | 处理自提任务和回执 | 骑行导航由 iPhone 与两块板直接完成 |

现有 [骑士导航控制器](../../app/骑士Knight-iOS/KnightApp/KnightRideNavigation.m) 和 [App 蓝牙实现](../../app/骑士Knight-iOS/KnightApp/KnightWebView.swift) 是手机端入口。AI-MAIN 的 [显示接线定义](../../firmware/xiaozhi-esp32/main/boards/esp32s3-ai-main/config.h) 配置为 240×240 SPI 显示，实际 HUD 模组到货后再核对接口、电压、引脚和驱动。 [车载 OLED 固件](../../firmware/knight_hud/knight_hud.ino)

## 蓝牙链路

- iPhone 区分「小智头显」和「车载屏」两种设备角色。App 分开管理设备标识、写入队列和重连。一路断开时，另一路仍接收指引。
- 小智在同一块板上增加独立的导航 GATT 特征，复用与手机的连接。订单回执保留现有用途，导航包由显示任务读取，收到距离更新时只刷新显示。
- 导航进行时优先保留 HUD 的转向与距离，语音对话与自提播报继续走现有音频流程。蓝牙接收只更新待渲染数据，屏幕刷新交给显示任务。
- 车载屏首版沿用现有 BLE 文本协议。比如 `D:右转|67米`，兼容固件可按现有两行布局显示。 [头显 BLE 协议](../hud/ai-hud-protocol.md)
- 手机端以导航会话 ID 和递增序号维护统一的当前状态。规划、正常导航、偏航重算、暂停、结束和到达都使用同一状态流。为旧车载固件转换成现有文本命令。小智新增导航特征可携带会话 ID、序号和有效时长，清除重复或过期数据。
- 导航更新以最新有效状态为准，合并待发的距离更新。断线、超时、结束或到达时清除旧转向。重连只补发当前仍有效的指引或明确状态。
- 蓝牙写入成功、固件收到、屏幕显示分别验证。双屏联调记录使用同一条指引的会话与序号核对。

小智的 Wi-Fi 和 BLE 共用无线资源。ESP32-S3 支持 Wi-Fi STA 与 BLE 同时保持连接，最终以语音播放期间的蓝牙延迟、掉线率和音频表现验收。 [ESP-IDF 5.4.4 射频共存](https://docs.espressif.com/projects/esp-idf/en/v5.4.4/esp32s3/api-guides/coexist.html)

## 联调顺序

| 阶段 | 做什么 | 通过条件 |
| --- | --- | --- |
| 模组到货前 | 用兼容的普通 OLED 验车载屏，复用同一条真实高德指引 | 先核对两行转向与距离，集成箭头布局后再验箭头和结束清屏 |
| 小智导航接入 | 用现有小智显示输出验证导航特征、渲染和语音回执并行 | 正常语音对话和播报期间，导航持续更新 |
| 两块板同时连接 | iPhone 同时连接小智和车载 ESP32，分别断开和恢复任意一路 | 两端收到同一条指引，单路掉线不影响另一路，重连恢复当前状态 |
| HUD 模组到货 | 按模组规格接入，再确认光学安装和视场 | 字符方向、亮度和可读性通过实屏验收 |
| 实地骑行 | 检查多次转向、偏航重算、定位中断、到达、后台和重连 | 手机与两屏保持一致，失效指引能及时退出显示 |

实测记录包括手机发出、每块板收到和完成显示的时间。对比静默与语音播放两种工况的延迟和漏包，分别记录两块板。两块屏的绘制时间允许不同，显示内容应来自同一条有效指引。
